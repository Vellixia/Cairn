# Data Model: Cairn MVP

**Feature**: `001-cairn-mvp` | **Date**: 2026-08-07

SQLite is the local source of truth and works offline. PostgreSQL holds a strictly
allowlisted shared subset for projects that were explicitly linked. Record identifiers are
UUIDv7 and stable across both, so sync is an upsert rather than a remap — with one
deliberate exception: the *project* key is translated from the local id to the
server-assigned shared id at the sync boundary (FR-064).

**Raw observations never leave the machine.** Referencing an observation as evidence does
not make it shareable; only its identifier, the evidence count, and an optional digest
travel (FR-055).

**What a handoff does carry.** FR-033 requires a handoff to state changed files, tests
executed, failures and decisions, and FR-055 allowlists handoffs — so a synced handoff
contains repository-relative **file paths** and short **derived statements** such as
`Test failed: cargo test --workspace`. These are the handoff's own derived fields, bounded
and redacted like everything else; they are not observation rows, and no observation field
is transmitted. A developer who does not want that leaving the machine should not link the
project, or should delete the handoff — both of which are supported.

## Conventions

- **Identifiers**: UUIDv7 everywhere, generated by whichever side creates the record.
  Time-ordered so they sort usefully and index well.
- **Timestamps**: UTC, stored as ISO-8601 text in SQLite and `timestamptz` in PostgreSQL.
- **Enums**: stored as lowercase text with a check constraint, not as integers. Readable
  in a database client, survives reordering.
- **Deletion**: soft-delete (`deleted_at`) for anything syncable, so a deletion can
  propagate as a tombstone. Content is cleared on delete; the row survives only as an
  identity so references stay resolvable. See "Deletion semantics" below.
- **Scope key**: a memory's scope is a pair — `scope` plus `scope_key`. `project` uses the
  project id, `branch` the branch name, `task` the task id, `session` the session id.

## Entities

### Project

The unit of ownership. One Git repository, however many worktrees.

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | PK — **local** identifier, never sent to the server as the project key |
| `name` | text | Defaults to the repository directory name |
| `git_common_dir` | text | Resolved Git common directory — local instance only |
| `repository_remote` | text? | First remote URL if one exists, normalized; a discovery *hint* |
| `linked` | bool | False until the user opts into server sync |
| `server_project_id` | uuid? | Server-assigned shared identity, set by `cairn link`; null while local-only |
| `created_at`, `updated_at`, `deleted_at` | timestamp | |

Rules: a project is created on first `cairn init`; two worktrees resolving to the same
Git common directory map to one local project.

**Local instance vs shared identity.** `git_common_dir` and worktree paths identify the
*local repository instance* and never leave the machine — `/Users/a/project` on a Mac and
`/home/a/project` on Linux are two instances of one shared project. The *shared* identity is
`server_project_id`, assigned by the server when `cairn link` creates a project and supplied
by the user when `cairn link` joins an existing one (FR-064). `repository_remote` may be used
to *suggest* a project to join, which the user confirms; it is never the sole authority, since
forks, mirrors, and remote-less repositories all break that assumption. Local ids are
translated to `server_project_id` at the sync boundary and nowhere else.

### Session

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | PK |
| `project_id` | uuid | FK → Project |
| `task_id` | uuid? | FK → Task; null for unbound sessions |
| `user_id` | uuid | Local user, or server user once linked |
| `agent` | text | e.g. `claude-code` |
| `branch` | text | At session start |
| `commit_sha` | text? | At session start; null in a repository with no commits |
| `worktree_path` | text | Local only; identifies the working context |
| `agent_session_key` | text | The agent's own session identifier from the hook payload; routes events to this session |
| `previous_session_id` | uuid? | FK → Session; the predecessor for this task or branch |
| `status` | enum | `active` \| `completed` \| `interrupted` |
| `started_at` | timestamp | |
| `ended_at` | timestamp? | Set when leaving `active` |
| `last_event_at` | timestamp | Local only; updated by the events already being written — reported, never used to reclassify |
| `last_turn_ended_at` | timestamp? | Local only; set by the `Stop` turn checkpoint, which never ends the session |
| `daemon_run_id` | uuid | Local only; the daemon run that last touched this session |
| `end_reason` | text? | From the `SessionEnd` payload's `reason` when one was delivered |
| `deleted_at` | timestamp? | |

Rules: **a session is identified by `id`, never by its worktree.** Any number of sessions
may be `active` at once, including two in the same worktree — the worktree is scope and
context, not a uniqueness key (FR-010). Uniqueness is
`(project_id, agent_session_key)` among non-deleted sessions, which makes session start
idempotent and routes every lifecycle event to the session that produced it. **Cairn cannot see whether an agent is alive** — the hook payloads carry no process
identity and no liveness signal (D16). Sessions therefore leave `active` only at
deterministic boundaries: a `SessionEnd` event, an explicit end command, or daemon start. A
`Stop` event is a turn boundary, not a session boundary — it records `last_turn_ended_at`
and the session stays `active` (D16).
On daemon start, every session still `active` — necessarily from a previous `daemon_run_id`
— is reconciled to `interrupted` and gets a handoff; if an event later arrives for that
session it is resumed to `active` under the current run, and the handoff already written
stands as a valid boundary record. Resuming clears `ended_at` and adopts the current
`daemon_run_id`; the handoff written at reconciliation keeps its own timestamp and its
`recovered` trigger. Nothing is guessed and nothing is lost either way.
`last_event_at` exists so `cairn status` can say how long a session has been idle; idleness
never reclassifies a session. `previous_session_id` is the most recently *ended* non-active session for
the same task, or failing that the same branch, with `id` breaking ties — a single link, not
a graph (FR-008). An agent with no session key of its own gets one synthesized per
connection, so manual MCP mode behaves the same way.

### Observation

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | PK |
| `session_id` | uuid | FK → Session |
| `type` | enum | `file_read` \| `file_changed` \| `command_run` \| `test_run` \| `error` \| `decision` \| `discovery` \| `user_instruction` |
| `occurred_at` | timestamp | |
| `branch`, `commit_sha` | text | Repository state at capture (FR-014) |
| `path` | text? | Repository-relative, for file observations |
| `command` | text? | Redacted, for command and test observations |
| `exit_code` | int? | |
| `outcome` | text? | `passed` \| `failed` \| `error` for `test_run` |
| `summary` | text | Bounded, redacted, human-readable one-liner |
| `details` | json? | Bounded structured fields; never a raw payload |
| `payload_bytes` | int | Asserted ≤ configured cap (default 4096) |
| `truncated` | bool | True when content was summarized to fit |
| `deleted_at` | timestamp? | |

Rules: written only after redaction and exclusion filtering. **Observations are local,
always.** No observation row, and no field of one — `summary`, `path`, `command`,
`details` — is ever transmitted, not in bulk and not as evidence for a shared memory or
handoff. A future explicit artifact-sharing feature could change that; this one does not.

### Memory

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | PK |
| `project_id` | uuid | FK → Project |
| `type` | enum | `fact` \| `decision` \| `convention` \| `failure` \| `procedure` |
| `scope` | enum | `project` \| `branch` \| `task` \| `session` |
| `scope_key` | text | Project id, branch name, task id, or session id |
| `content` | text | The knowledge itself, redacted |
| `state` | enum | `active` \| `stale` \| `superseded` |
| `superseded_by_id` | uuid? | FK → Memory |
| `origin_session_id` | uuid | FK → Session; provenance (FR-019) |
| `local_only` | bool | Never transmitted when true (FR-051) |
| `created_at`, `updated_at`, `deleted_at` | timestamp | |

**`memory_evidence`** join table: `(memory_id, observation_id, content_digest)` — the
observations that support a memory, **zero or more of them**. `origin_session_id` is
mandatory; evidence is not. A memory recorded in manual MCP mode or from the command line,
where automatic capture never ran, has an empty evidence set and a count of zero — that is a
valid, fully-provenanced memory, and Cairn never fabricates observations to fill the table
(FR-019). Provenance is the memory's origin session plus this set plus its count. The join row is retained when the observation is deleted, so the reference
stays resolvable and reports "evidence deleted" rather than vanishing (FR-052). Only
identifiers, the count, and the digest are ever shareable; observation content is local.

**`memory_fts`**: FTS5 virtual table over `content`, kept in sync by triggers. BM25 is
read from it; ranking then applies scope precedence and recency (D3).

Rules: only `active` memories are returned by default (FR-018). Superseding sets the
original to `superseded` and fills `superseded_by_id`; the original is retained. A memory
whose `scope_key` no longer resolves (deleted branch or task) is marked `stale` by a
reconciliation pass, not deleted.

### Handoff

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | PK |
| `session_id` | uuid | FK → Session |
| `trigger` | enum | `pre_compact` \| `session_end` \| `recovered` — a turn checkpoint (`Stop`) produces no handoff (FR-032, D16) |
| `goal` | text | From the bound task, or inferred from the session's instructions |
| `progress` | text | Derived summary of what moved |
| `completed_work` | json | List of derived statements |
| `remaining_work` | json | Unsatisfied acceptance criteria plus open failures |
| `changed_files` | json | Paths reconciled from `file_changed` + Git status |
| `decisions` | json | From `decision` observations and memories |
| `failures` | json | From `error` and failed `test_run` observations |
| `tests_executed` | json | From `test_run` observations with outcomes |
| `repository_state` | json | Branch, commit, working-tree status at generation |
| `next_step` | text | Derived recommendation |
| `agent_note` | text? | Bounded, clearly attributed agent narrative (FR-034) |
| `evidence` | json | Observation identifiers and count only — never their content |
| `created_at`, `deleted_at` | timestamp | |

Rules: a session may have several handoffs (compaction produces one and the session
continues); turn checkpoints produce none. The latest handoff for a session is the one a
successor briefing uses.

### Repository State

Not a table of its own for history — repository state is denormalized onto sessions,
observations, and handoffs at the moment of capture, and read live from Git for the
current briefing. This keeps the deterministic-boundary requirement (FR-014) without a
timeline nobody queries.

### Project Member

`(project_id, user_id, created_at)`. Flat membership — a user is a member or is not
(FR-057). No roles in this feature.

### API Token

Server-side: `id`, `user_id`, `name`, `token_hash`, `created_at`, `last_used_at`,
`revoked_at`. The plaintext token is shown once at creation and stored locally in the OS
keychain, or in a 0600 file where no keychain is available.

### Sync Outbox (local only)

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | PK |
| `project_id` | uuid | Local project id; only rows for linked projects are ever created |
| `server_project_id` | uuid | The shared identity actually sent (FR-064) |
| `entity_type` | enum | `project` \| `task` \| `session` \| `memory` \| `handoff` |
| `entity_id` | uuid | |
| `operation` | enum | `upsert` \| `delete` |
| `idempotency_key` | text | Unique; `entity_id` + content hash |
| `payload` | json | The record as it will be sent |
| `state` | enum | `pending` \| `in_flight` \| `delivered` \| `failed` |
| `attempts` | int | Incremented when the row is claimed, not when it is acknowledged |
| `last_error` | text? | |
| `claimed_at` | timestamp? | When the current drainer claimed the row; `NULL` unless `in_flight` |
| `created_at`, `delivered_at` | timestamp | |

Rules: the outbox row is written in the same transaction as the change it describes
(D9). No row is ever created for an unlinked project (FR-053, SC-010). `local_only`
memories never produce a row. There is no observation entity type — an outbox payload that
would carry observation content cannot be constructed, which is what makes SC-010's second
clause a property of the schema rather than a promise.

#### Writing under contention

Every local write goes through one mechanism (`crates/cairn-store/src/tx.rs`), because
contention is a property of the store, not of whichever repository happens to be writing.

SQLite's plain `BEGIN` is deferred: it takes no lock, and in WAL mode the transaction's
first statement fixes a read snapshot. A transaction that later writes must upgrade that
snapshot, and if another connection committed in between SQLite answers `SQLITE_BUSY_SNAPSHOT`
(517) — which `busy_timeout` cannot help with, because waiting does not make a stale snapshot
fresh. Write transactions therefore open with `BEGIN IMMEDIATE`, taking the write lock before
any snapshot exists. Contention then arrives only at the moment the lock is acquired, where it
is ordinary `SQLITE_BUSY`, and where retrying costs nothing because no work has been done yet.

Retries are bounded — ten attempts, exponential backoff to 400 ms with jitter — and apply only
to `SQLITE_BUSY` and `SQLITE_LOCKED` and their extended forms. Constraint violations,
corruption and malformed SQL keep their own result codes and fail immediately: retrying those
would turn a clear answer into a slow one. Single-statement writes outside a transaction are
retried too, since a statement that returned `SQLITE_BUSY` did not apply and replaying it
cannot duplicate anything. WAL stays on and readers stay concurrent throughout.

#### Claiming and recovery

The background worker and `cairn sync now` drain the same queue, so a row is **claimed**
before it is sent: one `UPDATE … RETURNING` moves eligible rows to `in_flight`, stamps
`claimed_at`, and returns only the rows that statement actually took. SQLite serializes
writers, so two drainers receive disjoint sets and neither can send a row the other owns.
No lease service, no lock manager, no broker (FR-059).

A row is eligible when it is `pending`, or when it is `in_flight` and its `claimed_at` is
older than a 60-second claim timeout — longer than the sync client's own 20-second request
timeout, so a drainer merely waiting on a slow server is never overtaken. That timeout is
the whole recovery mechanism: a drainer killed mid-send leaves a claim nobody will
acknowledge, and the next drain takes it back. Daemon start additionally releases every
standing claim at once, since nothing is draining yet and any claim still held belongs to a
run that is gone — the same reasoning as session reconciliation (D16).

`pending` in `cairn sync status` means *undelivered*, so it counts `in_flight` rows too:
what FR-058 reports is what has not reached the server, not what happens to be unclaimed at
that instant. A transient failure returns the row to `pending` immediately rather than
waiting out the timeout. `failed` stays reserved for permanent rejection and is never
reclaimed.

### Sync State (server)

`(idempotency_key, project_id, entity_type, entity_id, applied_at)` — the server's record
of what it has already applied. Redelivery is a no-op that returns the same result
(FR-056, SC-009).

The key is claimed with `INSERT … ON CONFLICT (idempotency_key) DO NOTHING` inside the same
transaction as the change, and the claim is what decides the outcome: inserting a row means
`applied`, inserting nothing means `duplicate`. Reading the key and then inserting it would
leave a window in which two concurrent deliveries of one key both read "unseen" — both
apply, and the loser fails on the primary key, surfacing a valid item as a permanent
rejection. Because the claim shares the transaction, an item that fails to apply releases
its key and can be retried.

## Relationships

```text
Project ─┬─< Task ──< Session
         ├─< Session ─┬─< Observation
         │            └─< Handoff
         ├─< Memory ──< memory_evidence >── Observation
         └─< ProjectMember >── User

Session ──> Session            (previous_session_id, optional, single link)
Memory  ──> Memory             (superseded_by_id, optional)
Memory  ──> Session            (origin_session_id, provenance)
```

## What syncs

| Entity | Syncs when project is linked (the allowlist) | Never syncs |
|---|---|---|
| Project | `server_project_id`, name, normalized remote | Local `id`, `git_common_dir`, worktree paths |
| Task | Title, goal, acceptance criteria, status | — |
| Session | Minimal provenance: id, agent, user, task, branch, commit, timings, status, end reason | `worktree_path`, `agent_session_key`, `daemon_run_id`, `last_event_at`, `last_turn_ended_at` |
| Memory | Type, scope, scope key, content, state, supersede link, provenance references | `local_only` memories, entirely |
| Handoff | The structured handoff, with evidence as identifiers and counts | — |
| Observation | **No observation row, and no observation field.** Identifiers, an evidence count and an optional digest travel as provenance *inside* a memory or handoff | Every observation row: `summary`, `path`, `command`, `details`, `outcome`, `exit_code` |
| Outbox | No | Entirely local |

An unlinked project produces no outbox rows at all, and no outbox row of any kind can carry
observation content — which is what makes SC-010 testable rather than aspirational.

## Deletion semantics

Deletion must remove what the user asked to remove and nothing else. A cascade that wipes
durable memory because its source session was deleted is a data-loss bug, not a feature.

| Delete | Effect | Left intact |
|---|---|---|
| Observation | Content fields cleared, `deleted_at` set. `memory_evidence` rows survive and resolve to "evidence deleted" | Every memory and handoff that referenced it, with its evidence count unchanged |
| Session | Session and its observations deleted as above; the session row survives as a tombstone so provenance still resolves | Memories and handoffs the session produced, their origin marked deleted. Adding `--with-memories` deletes them too — explicitly, never by default |
| Memory | That memory only, content cleared, tombstoned. Its `superseded_by` link is kept so the chain stays readable | Its evidence, its origin session, every other memory |
| Handoff | That handoff only, content cleared, tombstoned | The session, its observations, every memory |

Rules:

- Tombstones keep identity and timestamps; content is cleared, so nothing the user deleted
  is retained. Referential integrity survives without retaining what was removed.
- A tombstone for a record that was already shared produces an outbox `delete` item, applied
  idempotently server-side (FR-052).
- Purging tombstones is a maintenance concern, out of scope for this feature.

## Local schema notes

- WAL mode, `foreign_keys=ON`, busy timeout set for concurrent worktrees (D12).
- Indexes: unique `sessions(project_id, agent_session_key)` where not deleted,
  `sessions(project_id, worktree_path, status)`, `sessions(task_id, ended_at desc)`,
  `observations(session_id, occurred_at)`,
  `memories(project_id, scope, scope_key, state)`, `outbox(state, created_at)`.
- Migrations are versioned and forward-only; the local database records its schema
  version and refuses to open a newer one.
